# 项目定位与学习闭环设计

## 状态与背景

本文依据 2026-11-16 的项目讨论整理。项目名采用 agent-learn；定位是学习外骨骼，以轻量 Hook 配合 Markdown 规则辅助 AI 教学。后续用户已授权仅实现 DSH 插件；本文保留设计依据，具体落地与验证范围以 Project 为准。

现有学习体验需要用户反复要求“继续”“记录一下”，导致学习接续、状态维护和成果整理依赖用户逐项推动。项目希望由 AI 承担这些辅助工作，同时避免过快、过慢或不协调地带着用户走。

EMS 对话是需求示例，不是本项目必须内置的课程，也不是用户能力的正式评测证据。

## 定位与节奏边界

- 学习者决定方向、目标、深入程度和节奏；AI 承担既定目标内的教学组织与资料辅助。
- 正常讲解跟随当前意图和理解情况，主动性不等于每轮必须追加知识、考试或问题。
- 用户追问时处理追问，不急着拉回既定路线；用户明确要求继续时自然接续，不反复要求选择教学菜单。
- “明白了”不能单独作为进入新模块或判定掌握的开关；结合上下文判断是否继续。
- 存在理解障碍时缩小问题或改变呈现方式，不因一次错误就整段重学。
- 当前问题已闭合时可以自然停住。准备好下一步，不等于立即展开下一段。
- 一次推进一个适合当前理解情况的小单元；涉及学习者作答时等待反馈，不自行连续上课。

## 三个协作模块

### 学习状态

维护当前快照，支持主线、临时支线、返回位置、未解决问题和一个优先的下一动作。需要时允许暂挂多个问题，不将状态维护变成强制任务队列或僵硬的课程解锁关系。

例如主线是 EMS 设备约束，中途追问无功时，应保留主线及返回位置，补充当前需要的无功概念。支线学到目前够用后，从活跃问题中移除，保留有价值的认识和未解决缺口，再按对话意图回到主线。

“支线结束”“已经讲过”“用户表示理解”“有独立应用证据”是不同事实。退出活跃记录不意味着删除学习成果，也不意味着已经掌握。

### 阶段判断

判断当前问题是否形成完整认识、哪些缺口影响后续、是否值得沉淀或检验。评估主要在内部完成，不逐项播报流程。

| 情况 | 可选择的动作 |
| --- | --- |
| 存在阻碍当前理解的缺口 | 补充必要基础，或换一种讲法 |
| 关键能力缺乏证据，检验有实际价值 | 提供一个简短的新场景，不强制逢模块考试 |
| 形成可独立复用的认识 | 更新主题笔记或案例 |
| 已足以支持后续学习 | 准备自然接续，按当前意图决定是否展开 |
| 用户暂停 | 保存接续位置并结束 |

这些动作可以组合，但不因每轮回答结束就认定模块结束，不因单次答对或复述就写成永久掌握。

### 辅助执行与落盘

在已确认的学习工作区和记录范围内，发生实质变化时更新进度、活跃问题和接续位置；形成值得复用的认识时整理笔记，不要求用户每次显式下令。

普通重复解释、没有状态变化或只有零散聊天时不写文件。不逐轮追加日志，不把整堂讲解重复复制进进度、笔记和评测记录。长期目标、范围及重要资料的调整仍尊重用户决定。

学习数据保存在用户指定的学习工作区；项目自身的开发文档放在本仓库 Docs。规则、项目资料和学习者数据分别维护，避免混在一起。

## Hook 与规则的分工

正常教学规则负责节奏协调和自然衔接；结束 Hook 提供补漏机会，检查是否遗漏必要记录、支线收束或接续准备。检查的合法结果包括不做修改并结束。

计划借鉴 agent-docs：在一轮回答即将结束时提醒原 Agent 按需读取规则，不等待整个聊天关闭，也不启动独立评估 Agent。代码负责触发条件、防重复和异常放行；AI 负责语义判断与教学决策。

| 规则角色 | 预期职责 |
| --- | --- |
| principles | 定义外骨骼定位、自主权、节奏和证据边界 |
| init | 确认学习目标、工作区及记录范围，建立最小资料 |
| teaching | 讲解、支线处理、自然接续和按需检验 |
| maintain | 决定何时更新状态、沉淀成果和退出活跃问题 |
| spec | 规定计划、状态、知识笔记的内容归属与存储方式 |

上述规则分工已落实为仓库 rules/ 下的五份规则；构建为包内 defaults，首次使用补齐到可编辑用户目录。第一版采用简单结构，未引入数据库、复杂状态机、自动复习算法或独立评估 Agent。

Hook 只增加检查机会，不能保证教学判断正确。需要用真实学习场景校准节奏、落盘时机和支线处理。
